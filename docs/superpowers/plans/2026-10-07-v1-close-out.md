# v1 Close-Out Implementation Plan (plan 7)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fold the follow-ups the two reference samples surfaced into v1 and
cut the `1.0.0` release: an interlock logs `RESET_REFUSED` when it refuses a
reset; an `item-process-unit`'s hold message gives the wall time when a slowed
cycle made it differ from the hold time; `STALLED` and `OVERLOAD_TRIP` never
print their measured value on the wrong side of the threshold it crossed; the
two sample test helpers share one loader; and the repository gains a
`CHANGELOG.md`, `<Version>1.0.0</Version>` and a "Getting started" section.

**Architecture:** Three small event-text changes in `src/` — one branch in
`Dse.Control`'s `Interlock.Scan`, one field and one message in
`Dse.Components`' `ItemProcessUnit`, and an internal `ThresholdText` helper in
`Dse.Components.Mechanical` that `Motor` and `MotorStarter` format through
(R187: a minimal copy of the alarm's format-then-step arithmetic, since
`Dse.Components` cannot reference `Dse.Control`). No computed value changes:
no trip, stall, hold, reset or write happens on a different tick. A
`SampleFolder` class in `tests/Dse.Samples.Tests` becomes the one loader both
`Sample` and `WheelLine` delegate to, with their public members, every test
name and every assertion unchanged. The release is documentation plus one
MSBuild property and a two-fact `ReleaseTests` class that pins it. Three
goldens move, all in `samples/wheel-line/expected/`: `pyro-fail-high.log`
gains one line (Task 1), and three lines each of `slow-press.log` and
`stuck-kicker.log` gain the wall time (Task 2). Nothing else moves.

**Tech Stack:** .NET 10 (`net10.0`, SDK 10.0.401), C#, xUnit 2.9.3. No package
added or changed. JsonSchema.Net 8.0.5, test-only and pinned (unchanged).

## Review Focus

The five input classes the spec implies but does not name, most likely to bite
first. Each has its pinning test in the owning task.

1. **The boundaries of "refused".** A reset edge can arrive on a scan where
   the interlock is not tripped, on the very scan it trips, held high across
   several scans, or as a fresh edge after a refusal. The author expects only
   an edge that finds the interlock *already* latched with a condition still
   abnormal to log, once per edge (R184). Tests: Task 1,
   `AResetEdgeOnAnUntrippedInterlockLogsNothing`,
   `AResetEdgeOnTheTripScanIsNotARefusal`,
   `AResetWhileAConditionIsStillAbnormalIsRefused` (held high three scans: one
   `RESET_REFUSED`), `ARefusedResetSendsNoResetWrite` (two edges: two) and
   `AResetRefusedWhileAbnormalIsAcceptedOnTheNextEdgeOnceNormal`.
2. **A refused reset whose first abnormal condition is not the first out.** An
   interlock that tripped on condition 1 and then saw condition 0 go abnormal
   too has `FirstOut` 1; the spec says the message names "the first
   condition, in declared order, that is not normal" — condition 0. Test:
   Task 1, `ARefusedResetNamesTheFirstAbnormalConditionInDeclaredOrderNotTheFirstOut`.
3. **Hold and wall time that differ as doubles but not as text, or differ for
   a hold that is not timed.** "Differ" is decided on the two `F2` texts
   (R186): a cycle slowed by 0.1 % differs by 2.5 ms and must print one time;
   a slow-cycle cleared before Processing must print one time; a temperature
   hold under a full slow-cycle counts no hold time at all and must say so;
   a cycle that straddles the clear must give both. Tests: Task 2,
   `AHoldSlowedTooLittleToShowAtTwoDecimalsPrintsOneTime`,
   `ASlowCycleClearedBeforeProcessingLeavesTheMessageAsItWas`,
   `ATemperatureHoldUnderAFullSlowCycleGivesTheWallTime`,
   `AClearedSlowCycleLeavesTheHoldTimeAndTheWallTimeApart`, and the
   `normal-run` story's new absence (no hold message in an unslowed scenario
   carries ` elapsed)`).
4. **A measured value exactly on, or a decimal step beyond, its threshold.**
   A thermal state exactly at the trip level ("reached" is ≥, so it reads on
   the level, R188); a trip level with more than six decimals, where the cap

   `TheOverloadTripMessageNeverReadsBelowTheTripLevel` (rows `1.1234`/`1.1234`

## Decisions settled here (rulings R184–R193)

These refine the spec where the code, or a measured run, forced a choice. R193
gives the amendment note that records them in the spec.

- **R184 — Where a refusal is decided.** `Interlock.Scan` reads the `Reset`
  edge, then evaluates every condition (`allNormal`, and `first`, the lowest
  index that is not normal), then takes one of two branches: trip
  (`!allNormal && !_tripped`) or accept (`_tripped && resetEdge && allNormal`).
  The refusal is a third branch, `else if (_tripped && resetEdge)`, after
  both: it runs only when the interlock was latched *before* this scan (the
  trip branch did not run) and, the accept branch having failed, some
  condition is abnormal, so `first ≥ 0`. It raises `RESET_REFUSED` —
  `Reset refused: <tag> is not normal.` with `_conditions[first].Tag` — and
  writes nothing; the latch, `Tripped`, `Ok` and `FirstOut` are untouched.
  The spec says "while the interlock is tripped" without saying when; a reset
  edge on the scan that trips it is ruled **not** a refusal (the operator
  pressed reset before there was anything to refuse; the scan logs
  `INTERLOCK_TRIP` alone and the edge is consumed, as today). One event per
  rising edge: a held-high `Reset` logs once; each fresh edge logs again.
  `first` is the first abnormal condition in declared order, which is not
  necessarily `FirstOut` (the condition that tripped it).
- **R185 — What the refusal moves, measured.** Every golden in the solution
  was regenerated on a scratch copy of `179d4d1` with R184 applied:
  `samples/wheel-line/expected/pyro-fail-high.log` gains exactly one line,
  line 64 —
  `06:10:00.100  INT_BAY  RESET_REFUSED  Reset refused: Bay.Full is not normal.`
  — between the `Set to true.` write at 06:10:00.000 and the `Set to false.`
  write at 06:10:01.000 (65 events, from 64). No other golden moves: every
  reset in the mine-conveyor scenarios and in
  `tests/Dse.Control.Tests/Golden/conveyor-control.log` and
  `tests/Dse.Scenarios.Tests/Golden/*.log` is accepted. Two existing tests
  assert the old silence and change their expected codes:
  `InterlockTests.AResetWhileAConditionIsStillAbnormalIsRefused`
  (`INTERLOCK_TRIP` → `INTERLOCK_TRIP,RESET_REFUSED`, plus the message) and
  `InterlockTests.ARefusedResetSendsNoResetWrite` (→
  `INTERLOCK_TRIP,RESET_REFUSED,RESET_REFUSED`). Documentation that says a
  refused reset is silent, measured by grep over `README.md`, `docs/` (outside
  `docs/superpowers/`) and `samples/`: `samples/wheel-line/README.md` ("A
  refused reset logs nothing: …") and `docs/control-blocks.md` (the
  interlock's event list; "a refused reset sends nothing" stays true and gains
  "and logs why"). `DocumentationTests.TheControlBlocksPageNamesEveryBlockEveryEventAndEveryDiagnostic`
  gains the code and the example message; the `pyro-fail-high` story gains
  the line; its README block quotes it and the release write after it.
- **R186 — Hold versus wall time: `item-process-unit` only; "differ" is the
  `F2` text.** `BulkProcessUnit` has the same `_elapsed` hold timer but no
  `slow-cycle` fault (its faults are `discharge-jam` and `yield-loss`): its
  timer advances by `ctx.Dt` on every Processing tick, so hold and wall time
  are always the same and its message is unchanged. `ItemProcessUnit` gains
  `_wall`, zeroed with `_elapsed` in `StartProcessing` and advanced by
  `ctx.Dt` on every Processing tick beside `_elapsed += ctx.Dt * (1 −
  _slowFraction)`. At release both are formatted `F2` (invariant); if the two
  texts are ordinally equal the message is exactly today's
  (`Hold satisfied after 2.00 s; discharging 3 items.`), otherwise
  `Hold satisfied after 2.00 s of hold (4.00 s elapsed); discharging 3 items.`.
  Comparing texts, not doubles, is chosen because a message that printed
  `2.50 s of hold (2.50 s elapsed)` would contradict itself (measured:
  fraction 0.001 gives 2.4975 s of hold in 2.5 s, both `2.50`); with
  `_slowFraction` 0 the two sums are the same double sequence, so every
  unslowed message is unchanged by construction. A hold that is not timed
  still counts its timer at the slowed rate, so a temperature hold under a
  full slow-cycle prints `0.00 s of hold (2.00 s elapsed)` — the truth about
  the counter, which today prints `0.00 s` alone. Measured goldens: in
  `slow-press.log` lines 64 and 75 (`40.00 s of hold (400.00 s elapsed)`) and
  94 (`40.08 s of hold (65.10 s elapsed)`, the cycle the clear at 1140 s falls
  in); in `stuck-kicker.log` lines 65, 76 and 88, the same three messages.
  Event counts unchanged (267, 271). No other golden has a slowed hold. One
  existing test changes: `ItemProcessUnitTests.ASlowCycleStretchesATimedHoldByOneOverOneMinusTheFraction`
  asserted `2.00 s` for every fraction; it gains a `message` column (rows 0.5
  and 0.75 give the wall time, rows 0.0 and −1.0 do not). The 6b.1 test
  `TheHoldSatisfiedMessagePrintsSecondsToTwoDecimals` and
  `BulkProcessUnitTests`' message are unchanged.
- **R187 — `ThresholdText` lives in `Dse.Components.Mechanical`, internal; the
  alarm keeps its own copy.** `Dse.Components` references `Dse.Core` only and
  `Dse.Control` references `Dse.Io.Abstractions` only; the one assembly both
  see is `Dse.Io.Abstractions`, the scan-block contract that an application
  under test or a protocol adapter references without the engine — a
  message-formatting helper is not part of that contract, and making it
  public there for two call sites would widen it. The helper copies the
  alarm's arithmetic (`Alarm.Display`, 6e R145: format with `F<n>`, parse
  back, step one unit in the last place in `decimal`, never scale) and its
  decimal count (`limit.ToString("R")`, mantissa decimals minus exponent,
  floored at 0), about twenty lines. `Alarm` is not touched, so no alarm
  golden can move. `Dse.Components` already has
  `InternalsVisibleTo Dse.Components.Tests`, but the tests drive the helper
  through `Motor` and `MotorStarter`, as a reader of the log sees it.
- **R188 — `OVERLOAD_TRIP` never reads *below* the trip level; on it is
  right.** The spec says the thermal state is "rounded away from (up past) the
  trip level by format-then-step" and that "no golden moves for this item".
  Measured, the two cannot both hold: stepping up whenever the `F3` text lies
  below the *value* (R145's rule for an alarm raise) turns the chute-blockage
  golden's `Thermal state 1.100 reached the trip level 1.1.` (thermal
  1.1000357303409216) into `1.101` — moving
  `samples/mine-conveyors/expected/chute-blockage.log`, the mine-conveyor
  README's quote of it, and the 6e test row
  `TheOverloadTripMessagePrintsTheThermalStateToThreeDecimals(1.1000357303409216, …)`,
  which R148 recorded as deliberate. The trip condition is `thermal >=
  TripLevel` — "reached" — so a value that reads *on* the level is true; only
  one that reads *below* it is wrong (the 6e follow-up: a trip level of
  1.1234 printed `1.123`). Chosen: `n = min(max(3, d + 1), 6)` decimals, `d`
  the trip level's decimals as the alarm counts them; the nearest `F<n>` text;
  stepped up once, in `decimal`, only if that text parses below the trip
  level. With `d ≤ 5` the nearest text of a value ≥ the level is never below
  it (the level lies on the `n`-decimal grid); the cap bites at `d ≥ 6`, and
  the step can only act when `d ≥ 7` (measured: a level of 1.234567, `d` 6,
  is never stepped). For the shipped level 1.1, `n` is 3 — today's `F3` —
  and the nearest rounding is today's, so nothing moves (measured: no golden
  changes, every existing test passes). R188 and R189 supersede 6e R148
  ("only the alarm rounds away from a configured value") for `OVERLOAD_TRIP`
  and `STALLED`; the alarm is unchanged.
- **R189 — `STALLED` rounds the demand up, and above the breakdown's text.**
  The spec: "the torque demand is rounded up at `F0` (never shown at or below
  the breakdown torque it exceeds); the breakdown torque is formatted as
  today". Rounding up alone fails its own parenthesis when the breakdown's
  `F0` text rounds up to the demand's ceiling: breakdown 12.6 prints `13`, and
  a demand of 12.7 rounded up is `13` too (`13 exceeds 13`). Chosen: the
  demand's `F0` text rounded up (format, step once when it parses below the
  demand); if that does not exceed the breakdown's text (compared as
  `decimal`), the breakdown's text plus one. Measured: no golden has a
  `STALLED` line; the existing
  `TheAtSpeedAndStalledMessagesPrintSpeedToOneDecimalAndTorqueToWholeNewtonMetres`
  (`Torque demand 13 N·m exceeds breakdown torque 12 N·m.`, an exact 13 over
  12.5) passes unchanged. A demand of 14.2 now prints `15` where it printed
  `14`: rounding up is the spec's choice, recorded so a reviewer does not
  "fix" it. `decimal` cannot hold a value of magnitude 7.9 × 10²⁸ or more, nor
  a non-finite one, where today's message printed: `Exceeding` returns the
  plain `F<n>` text for such a value (measured: a demand of 1e30 prints
  `1000000000000000019884624838656`, as today, instead of throwing). Pinned
  by the stall theory's fourth row.
- **R190 — The shared loader is an instance class; the two helpers keep their
  surface.** `SampleFolder(folder)` holds a sample's paths (`Root`, `Plant`,
  `Readme`, `SourceRoot`, `Scenario`, `Golden`, `SourceGolden`), its run
  cache (`Run`) and `Load(name)`, which parses the scenario, loads its plant
  with the scenario's load options through `Sample.Catalogue`, builds it,
  schedules every timeline action through `Sample.Schedule`, and returns a
  `LiveScenario(Simulation, Step, Ticks)` not yet ticked. `Sample` and
  `WheelLine` each hold one in a `private static readonly SampleFolder Folder`
  declared first, and every path member becomes an expression-bodied
  property over it, so no static initialiser reads `Folder` before it is set.
  `Sample.Catalogue`, `Sample.Updating` and `Sample.Schedule` stay on `Sample`
  (both samples and many tests use them); `Sample.Trace` and
  `WheelLine.Watch` keep their loops and signatures and start from
  `Folder.Load`. `SourceRoot` is now found from `SampleFolder.cs`'s
  `[CallerFilePath]`, in the same folder as before. The one observable
  difference: a scenario that does not parse now throws with its diagnostics
  (`'<name>' does not parse: …`, the run cache's form) from `Trace` and
  `Watch` too, where they said `'<name>' does not parse.` — no test reaches
  it. Measured: 134 tests before and after, all passing, no test file but the
  two helpers changed.

```csharp
/// threshold it crossed, so the text never reads on the wrong side of it

    /// <summary>
    /// The decimals of a level's shortest round-trip form, as the alarm counts
    /// them: <c>1.1</c> has 1, <c>1.125</c> 3, <c>2</c> 0, <c>1E-07</c> 7.
    /// </summary>
    public static int Decimals(double level)
    {
        string shortest = level.ToString("R", CultureInfo.InvariantCulture);
        int e = shortest.IndexOf('E', StringComparison.Ordinal);
        int exponent = e < 0 ? 0 : int.Parse(shortest.AsSpan(e + 1), NumberStyles.AllowLeadingSign, CultureInfo.InvariantCulture);
        string mantissa = e < 0 ? shortest : shortest[..e];
        int dot = mantissa.IndexOf('.', StringComparison.Ordinal);
        return Math.Max(0, (dot < 0 ? 0 : mantissa.Length - dot - 1) - exponent);
    }

    /// <summary>
    /// <paramref name="value"/>, which has reached <paramref name="level"/>,
    /// to <paramref name="decimals"/> places: the nearest text, stepped up
    /// once only if it reads below the level. A value on the level reads on it.
    /// </summary>
    public static string NotBelow(double value, double level, int decimals)
    {
        string text = Format(value, decimals);
        return double.Parse(text, CultureInfo.InvariantCulture) < level ? StepUp(text, decimals) : text;
    }

    /// <summary>
    /// <paramref name="value"/>, which exceeds a limit printed as
    /// <paramref name="limitText"/>, to <paramref name="decimals"/> places:
    /// rounded up (the nearest text, stepped once when it lies below the
    /// value), and one step above the limit's text if that still does not
    /// exceed it. A non-finite value, or one beyond <c>decimal</c>'s range,
    /// prints as its plain text.
    /// </summary>
    public static string Exceeding(double value, string limitText, int decimals)
    {
        if (!double.IsFinite(value) || Math.Abs(value) >= 7.9e28)
        {
            return Format(value, decimals);   // beyond decimal's range: the plain text, as before
        }

        string text = Format(value, decimals);
        if (double.Parse(text, CultureInfo.InvariantCulture) < value)
        {
            text = StepUp(text, decimals);
        }

        return decimal.Parse(text, CultureInfo.InvariantCulture) > decimal.Parse(limitText, CultureInfo.InvariantCulture)
            ? text
            : StepUp(limitText, decimals);
    }

    private static string Format(double value, int decimals) =>
        value.ToString("F" + decimals.ToString(CultureInfo.InvariantCulture), CultureInfo.InvariantCulture);

    private static string StepUp(string text, int decimals) =>
        (decimal.Parse(text, CultureInfo.InvariantCulture) + new decimal(1, 0, 0, false, (byte)decimals))
            .ToString("F" + decimals.ToString(CultureInfo.InvariantCulture), CultureInfo.InvariantCulture);
}
```

```csharp
using System.Collections.Concurrent;
using System.Runtime.CompilerServices;
using Dse.Configuration;

namespace Dse.Samples.Tests;

/// <summary>
/// One sample folder, the loader both sample helpers share (plan 7, R190): its
/// files, read from the copy in the test output and written — only when
/// DSE_UPDATE_GOLDEN=1 — at their source under <c>samples/&lt;folder&gt;/</c>;
/// its scenarios' runs, cached; and a scenario loaded live with its timeline
/// scheduled. <see cref="Sample"/> holds the mine conveyors' and
/// <see cref="WheelLine"/> the wheel line's.
/// </summary>
public sealed class SampleFolder
{
    private readonly ConcurrentDictionary<string, Lazy<ScenarioRunResult>> _runs = new(StringComparer.Ordinal);

    /// <summary>The sample under <c>samples/<paramref name="folder"/>/</c>, copied to <c><paramref name="folder"/>/</c> in the test output.</summary>
    public SampleFolder(string folder)
    {
        ArgumentException.ThrowIfNullOrWhiteSpace(folder);
        Folder = folder;
        Root = Path.Combine(AppContext.BaseDirectory, folder);
        SourceRoot = FindSourceRoot(folder);
    }

    /// <summary>The folder's name, the same under <c>samples/</c> and in the test output.</summary>
    public string Folder { get; }

    /// <summary>The copy in the test output, which the tests read.</summary>
    public string Root { get; }

    public string Plant => Path.Combine(Root, "plant.json");

    public string Readme => Path.Combine(Root, "README.md");

    /// <summary>The sample's folder in the repository, found from this source file.</summary>
    public string SourceRoot { get; }

    public string Scenario(string name) => Path.Combine(Root, "scenarios", name + ".json");

    public string Golden(string name) => Path.Combine(Root, "expected", name + ".log");

    public string SourceGolden(string name) => Path.Combine(SourceRoot, "expected", name + ".log");

    /// <summary>
    /// A scenario's run through the same runner <c>dse run</c> uses, once per test
    /// process: a run is deterministic, so every test that reads it shares it.
    /// </summary>
    public ScenarioRunResult Run(string name) =>
        _runs.GetOrAdd(name, n => new Lazy<ScenarioRunResult>(() => RunOnce(n))).Value;

    /// <summary>
    /// A scenario loaded live: its plant built with the scenario's load options and
    /// every timeline action scheduled through <see cref="Sample.Schedule"/>, not yet
    /// ticked. The caller ticks it <see cref="LiveScenario.Ticks"/> times to run it
    /// to its full duration.
    /// </summary>
    public LiveScenario Load(string name)
    {
        string path = Scenario(name);
        ScenarioParseResult parsed = ScenarioLoader.Parse(File.ReadAllText(path));
        Scenario scenario = parsed.Scenario ?? throw new InvalidOperationException($"'{name}' does not parse: {parsed.ToText()}");
        LoadResult load = PlantLoader.Load(File.ReadAllText(scenario.ResolvePlantPath(path)), Sample.Catalogue, scenario.ToLoadOptions());
        Simulation simulation = load.Builder?.Build() ?? throw new InvalidOperationException(load.ToText());
        foreach (ScenarioAction action in scenario.Timeline)
        {
            Sample.Schedule(simulation, action);
        }

        TimeSpan step = load.Options!.TimeStep;
        return new LiveScenario(simulation, step, scenario.Duration.Ticks / step.Ticks);
    }

    private ScenarioRunResult RunOnce(string name)
    {
        string path = Scenario(name);
        ScenarioParseResult parsed = ScenarioLoader.Parse(File.ReadAllText(path));
        Scenario scenario = parsed.Scenario ?? throw new InvalidOperationException($"'{name}' does not parse: {parsed.ToText()}");
        ScenarioRunResult result = ScenarioRunner.Run(scenario, File.ReadAllText(scenario.ResolvePlantPath(path)), Sample.Catalogue);
        return result.IsValid ? result : throw new InvalidOperationException($"'{name}' does not run: {result.ToText()}");
    }

    private static string FindSourceRoot(string folder, [CallerFilePath] string thisFile = "") =>
        Path.GetFullPath(Path.Combine(Path.GetDirectoryName(thisFile)!, "..", "..", "samples", folder));
}

/// <summary>A scenario's simulation, built and scheduled, with its step and the number of ticks its duration takes.</summary>
public sealed record LiveScenario(Simulation Simulation, TimeSpan Step, long Ticks);
```

```csharp
    {

        TimeSpan step = live.Step;
        if (every < step || every.Ticks % step.Ticks != 0)
        {
            throw new ArgumentOutOfRangeException(nameof(every), every, $"Sample every whole number of {step.TotalMilliseconds} ms steps, at least one.");
        }

        long stride = every.Ticks / step.Ticks;
        var traces = tags.ToDictionary(t => t, _ => new List<TagSample>(), StringComparer.Ordinal);
        for (long tick = 1; tick <= live.Ticks; tick++)
        {
            live.Simulation.Tick();
            if (tick % stride == 0)

                TimeSpan time = TimeSpan.FromTicks(step.Ticks * tick);
                foreach (string tag in tags)
                {
                    traces[tag].Add(new TagSample(time, live.Simulation.IO.Read(tag).AsDouble));
                }
            }
        }

        return traces.ToDictionary(p => p.Key, p => (IReadOnlyList<TagSample>)p.Value, StringComparer.Ordinal);
    }

    /// <summary>Schedules one scenario action on a live simulation, the way <c>ScenarioRunner</c> does, so a recorder sees it.</summary>
    public static void Schedule(Simulation simulation, ScenarioAction action)
    {
        ArgumentNullException.ThrowIfNull(simulation);
        switch (action)
        {
            case WriteAction write:
                TagKind kind = simulation.IO.Directory.Find(write.Tag).Kind;
                TagValue value = write.Value.ToTagValue(kind)
                    ?? throw new InvalidOperationException($"'{write.Tag}' cannot take {write.Value}.");

                break;
            case FaultAction fault:
                simulation.InjectFaultAt(fault.At, fault.ComponentId, fault.FaultId, new FaultArguments(fault.Arguments.ToArray()));
                break;
            case ClearAction clear:
                simulation.ClearFaultAt(clear.At, clear.ComponentId, clear.FaultId);
                break;
            default:
                throw new InvalidOperationException($"'{action?.GetType().Name}' is not a scenario action.");
        }
    }
```
